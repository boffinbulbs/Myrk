# Verification scope

The stored proof laboratory has a standalone dependency graph. Changes confined to research/storage-pcs select its Windows and Linux proof jobs and the reference model. Before omitting shared steps, the selector checks tracked Cargo manifests for incoming paths and workspace membership. An introduced dependency, ambiguous manifest or unavailable boundary selects shared checks. The shared Rust and conditional row matrix jobs remain present and explicitly record that their steps are outside that isolated change scope.

Every other changed path selects the full shared suite. This includes shared storage, root manifests, workflow code, documentation outside the laboratory and unknown files. Manual runs, new branches, unavailable revisions, malformed events and scope errors also select shared checks. The selector reads both sides of renames as separate paths so moving shared source into the laboratory cannot hide its deletion.

The scope job checks a bounded available Git range. A shallow checkout that lacks either endpoint falls back to shared checks. Reference and stored proof jobs always run. Scope failure leaves the core output unset, which also selects shared steps. Cancellation still stops dependent work. Existing matrix job names are preserved. These conditions follow GitHub's documented [job dependencies](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idneeds) and [status functions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions).

Selector tests cover canonical paths, shared and unknown paths, missing and invalid ranges, push and pull request ranges, an actual Git rename, incoming path dependencies, wildcard workspace membership and malformed manifests. The Linux scope job uses Python 3.11 or newer for the standard TOML parser. Workflow and selector changes themselves select the full suite. A scope result describes which checks were selected and does not claim that omitted steps executed.

Signature scheduling and signature construction use separate Windows and Linux jobs. The original scheduling job names remain stable. Each job retains a 15 minute deadline and serial compilation. Every original check command is retained once per platform, with each result producer and its comparison in the same job. Construction uses the tracked source certificate fixture and its own generated route and symbolic records.

This partition addresses the complete combined job reaching its deadline during compilation. It changes the grouping of checks, with their proof parameters, resource arguments, environment gates and validation commands preserved.
