# Aegis architecture figures

This directory retains reproducible figures for the later [Thorum Aegis Protocol](../../docs/aegis.md). The figures describe architecture and an illustrative ordering. They are not execution results, consensus simulations, privacy measurements or latency benchmarks. Aegis has no runtime implementation. The initial chain milestone retains checkpoint finality before onward spending.

## Figures and definitions

| Figure | Meaning |
|---|---|
| [Private payment flow](figures/aegis-architecture.svg) | C constructs a complete private payment, S commits valid state, Y privately recovers and spends, Z receives the next certified output, M records and N independently verifies |
| [Certification and recording](figures/aegis-certification-order.svg) | Certification sequence q advances before the mined recording cursor k in a fixed illustrative example |

C, Y and Z are independent wallets. S denotes eligible stakers, M a miner and N an ordinary validating node. These are role labels. Diagram arrows describe messages and local actions rather than public links between consumed private notes.

The [figure data](figure-data.json) records four illustrative states: (q,k) equals (0,0), (1,0), (2,0) and (2,2). Certification advances one authoritative private state, and later mining records its contiguous prefix. The example has no elapsed time axis or claim that a work block must wait until both payments commit. Its ordering is a later acceptance scenario to demonstrate under controlled tests.

The protocol requirements include

$$
S_q=\operatorname{Apply}(S_{q-1},B_q),\qquad 0\le k_h\le q.
$$

The figures do not implement Apply, a private proof, eligibility, weighted consensus, data availability, auxiliary work or replay. The [architecture specification](../../docs/aegis.md) states those obligations, missing constructions and delivery gates. The eight second consensus experiment target has no supporting timing data and is not plotted.

## Reproduction

SVG and JSON generation uses the Python standard library. From this directory:

```text
python generate_figures.py
python generate_figures.py --check
```

The check requires exact generated bytes, valid XML, bounded numeric coordinates and declared labels. SVG text uses the declared system font fallback. The generator and explicit geometry are original project material. No upstream code, diagrams or font files are copied into this directory.

PNG previews use the same geometry through optional Pillow rendering. Their exact reproduction additionally requires the recorded font bytes and software versions:

```text
python generate_figures.py --png
python generate_figures.py --check --png
```

The retained previews were generated on Windows with Python 3.12.14 and Pillow 12.3.0. Arial regular and bold font fingerprints are recorded in [source_record.json](source_record.json). Font files are not distributed. These optional PNG dependencies do not affect the standard library SVG and JSON check.

## Primary research boundary

The architecture evaluates a complete round based state machine with justified locks, durable signing and explicit commit decisions. Its weighted confidential and post quantum adaptation remains unimplemented and requires its own safety, liveness and privacy analysis.

1. [Consensus state machine and lock rules](https://github.com/cometbft/cometbft/blob/d03254d3599b973f979314e6383b89fa1802e679/spec/consensus/consensus.md).
2. [Signing state and conflicting message prevention](https://github.com/cometbft/cometbft/blob/d03254d3599b973f979314e6383b89fa1802e679/spec/consensus/signing.md).
3. [Durable signing and replay](https://github.com/cometbft/cometbft/blob/d03254d3599b973f979314e6383b89fa1802e679/spec/consensus/wal.md).
4. [Buchman, Kwon and Milosevic, The latest gossip on BFT consensus, revision 3](https://arxiv.org/abs/1807.04938v3).
5. [Yin, Malkhi, Reiter, Gueta and Abraham, HotStuff: BFT Consensus in the Lens of Blockchain, revision 6](https://arxiv.org/abs/1803.05069v6). This is a comparison reference, without adoption of its certificate or commit construction.
6. [FIPS 204, Module Lattice Based Digital Signature Standard](https://csrc.nist.gov/pubs/fips/204/final).

The source snapshot is an inspection reference, not a recommendation to deploy that historical release. No referenced code is imported and no project dependency changes. The figures and specification do not inherit an implemented consensus protocol or a combined security level from these references.
